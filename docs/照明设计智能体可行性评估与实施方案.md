# 照明设计智能体可行性评估与实施方案

> 评估日期：2026-08-20
> 
> 结论先行：当前项目已经具备“可审计的室内照明设计协作智能体”基础，可以进入试点；暂不具备无人值守地从 CAD 直接生成合规设计并签发成果的条件。推荐路线是由大模型负责理解、检索和流程编排，由确定性计算、配光文件和 DIALux/Relux/Radiance 负责工程计算，由工程师在关键闸门处确认。

## 2. 行业形态判断

公开可用的照明软件大多是计算/建模工具，不是可以独立签发成果的通用智能体。可落地的产品形态通常是五层组合：

1. 需求与资料助手：解析任务书、图纸和标准，形成有来源的任务书；
2. 方案编排器：调用规则、初算、灯具目录和仿真工具；
3. 确定性计算器：执行流明法、点光源/光度计算和规则比较；
4. 专业仿真器：DIALux evo、Relux 或 Radiance 完成空间级照度、均匀度、UGR 等计算；
5. 交付与审计层：冻结版本、记录输入快照、输出报告并保留人工签发责任。

因此，真正的差异化不在“让 LLM 自己算照度”，而在于把证据、版本、配光资产、仿真结果和接受记录串成可追溯闭环。

## 4. 当前智能体能力盘点

### 4.1 已具备、可直接形成产品价值的能力

| 能力 | 当前实现 | 产品含义 |
|---|---|---|
| 项目事实与版本 | `ProjectState`、SQLite、不可变 revision、乐观锁 | 聊天不是事实源，能追查“谁在什么版本确认了什么” |
| 证据检索 | Chroma/SQLite 双后端、文档哈希、证据块 ID、定位信息 | 标准数值可引用，支持离线优先 |
| 自动补参 | `search_evidence` + `apply_rag_lighting_parameters` | 能在证据明确时自动补充照度、CCT、Ra、UGR、U0、LPD |
| 确定性初算 | 流明法及输入、假设、限制持久化 | 可快速估算灯具数量和功率密度，但不会冒充精算 |
| 规则校核 | 显式 `RuleRequirement` + 证据 ID | 规则结论可复现，缺证据或观测值时不会虚报合格 |
| 灯具检索 | DIALux 两阶段查询、详情解析、条件复核、缓存/熔断/限流 | 可从真实目录建立候选池，字段缺失会标注不完整 |
| 配光资产 | ZIP 安全校验、IES/LDT/ULD 解压、SHA-256、项目级存储 | 最终型号的资产可审计地交给 DIALux |
| CAD 接入 | DXF，及安装 ODA Converter 时的 DWG；面积/边界候选 | 能减少面积和房间名称录入，但几何仍需确认 |
| DIALux 交接 | `handoff_id`、`input_snapshot_sha256`、任务包 ZIP | 把“模型建议”与“人工仿真输入”绑定起来 |
| 结构化结果回灌 | API/CLI 已能接收指标并判断 matched/mismatch 等状态 | 已具备仿真闭环的第一阶段数据契约 |
| 交互与审计 | FastAPI、Next.js、NDJSON 工具轨迹、Markdown 报告 | 能以工作台方式试点，而不是只提供命令行脚本 |

### 4.2 当前不能承诺的能力

- 没有 IES/LDT 光强分布解析和浏览器照度热力图；
- 没有服务端高可信照度、均匀度或 UGR 求解器；
- 没有自动布灯、回路/功率优化或 A/B/C 方案搜索；
- 没有稳定的 DIALux PDF/CSV 自动解析、自动规则重跑和修订循环；
- 没有 `DesignAcceptance` 和模板驱动的正式 PPTX/PDF 发布；
- 在线 RAG 来源抓取、审批和许可证治理尚未实现；
- 文档中提到的 `import_selected_luminaires_to_dialux` 当前不在 `agent.py` 的实际工具列表，不能当作已经可用的智能体能力。

## 5. 推荐产品定位

产品名称建议为“可审计室内照明设计工作台”，而不是“自动照明设计师”。首个目标用户是室内/建筑照明工程师和项目负责人，首个高价值场景是办公室、会议室、视频会议室等规则相对清晰的室内空间。

### 5.1 人机协作责任边界

| 决策 | 智能体 | 确定性服务 | 工程师/用户 |
|---|---|---|---|
| 需求理解、资料定位 | 负责 | 提供结构化字段 | 确认冲突和缺失项 |
| 标准参数 | 检索并解释 | 保存证据和版本 | 选择适用标准/批准来源 |
| 灯具候选 | 组织搜索和比较 | 解析、筛选、记录供应商数据 | 确认最终型号组合 |
| 初算/规则 | 解释结果 | 执行计算和比较 | 判断是否继续深化 |
| DIALux/Relux/Radiance | 创建任务、读取结果 | 校验输入快照 | 运行、复核、修订模型 |
| 正式交付 | 组织内容 | 从冻结快照渲染 | 接受、签发并承担专业责任 |

### 5.2 推荐状态机

```text
draft
  -> brief_confirmed
  -> preliminary_calculated
  -> luminaires_selected
  -> simulation_pending
  -> simulation_verified
  -> accepted
  -> delivered
                 \-> needs_revision -> simulation_pending
```

每个箭头都应由工具或用户动作触发。LLM 不得直接修改状态，也不能跳过“最终灯具确认”“输入匹配”“用户接受”三个闸门。

## 6. 可行的目标架构

### 6.1 逻辑分层

```text
Next.js 工作台
  -> FastAPI 适配层
     -> Agent Orchestrator（理解、检索、工具编排）
        -> ProjectStore / EvidenceStore / AssetStore
        -> Deterministic Lighting Services
           - preliminary calculation
           - rule engine
           - photometry parser
           - layout optimizer
        -> Solver Adapters
           - DIALux handoff/import
           - RELUX structured result
           - Radiance batch solver（后续）
        -> Delivery Service
           - acceptance snapshot
           - template renderer
           - artifact audit
```

### 6.2 需要新增的领域对象

建议在现有模型上增量扩展，不另起数据库：

```text
PhotometryProfile
  luminaire_id, file_type, source_sha256, parsed_fields, parser_version

LayoutCandidate
  project_revision, solver_version, placements, constraints, objective, status

SimulationResultArtifact
  source_file, source_sha256, parser_version, extracted_metrics, raw_locator

DesignAcceptance
  project_revision, verified_result_id, accepted_by, accepted_at, note

DeliverableTemplate
  template_id, kind, template_sha256, field_schema, approval_status
```

所有新增对象都应携带项目 revision、源文件哈希和版本；不可把解析后的数字覆盖掉原始证据。

### 6.3 推荐 API 增量

第一批：

```text
POST /api/projects/{id}/photometry/parse
POST /api/projects/{id}/simulation-results/import
POST /api/projects/{id}/simulation-results/{run_id}/verify
POST /api/projects/{id}/review-simulation
```

第二批：

```text
POST /api/projects/{id}/layout-candidates
GET  /api/projects/{id}/layout-candidates
POST /api/projects/{id}/acceptance
POST /api/projects/{id}/deliverables/templates/{template_id}/render
```

第一批应优先复用现有 `SimulationRun`，避免同时引入两套结果模型；第二批在验收记录稳定后再增加模板和优化器。

## 7. 分阶段实施计划

### 阶段 0：基线和试点准备（1 周）

目标：让当前实现成为可演示、可回归的基线。

- 对齐方案文档和 `agent.py` 工具清单，删除或标注未实现工具；
- 固定 3 类模板：普通办公室、会议室、视频会议室；
- 准备 10 个脱敏项目，至少包含 DXF、标准资料、灯具候选和一次 DIALux 结果；
- 固定 CI 命令和测试数据，不在测试中访问真实 LLM、Chroma 或 DIALux。

验收：同一输入可重复产生相同 revision、计算结果和报告；任何旧仿真在任务书/灯具变更后变为 `stale`。

### 阶段 1：仿真结果回灌闭环（2～3 周，最高优先级）

目标：把“交接包 → DIALux/Relux → 结果 → 修订”做成真正可用的工作流。

- 支持受控 CSV/JSON 和人工表单；PDF 解析先只覆盖固定报告模板；
- 解析维持照度、最小照度、U0、UGR、LPD 及来源定位；
- 校验 `handoff_id`、项目 revision、最终灯具 ID、配光 SHA-256；
- `matched` 才允许自动重跑规则；`mismatch/incomplete/unverified` 只能作为参考；
- 由工具生成下一次修改任务，不让模型自行改写工程事实。

验收指标：

- 结构化字段解析准确率 ≥ 98%；
- 错配项目/灯具/配光的拦截率 100%；
- 10 个基准项目均能完成至少一轮“导入—校验—修订”闭环。

### 阶段 2：配光解析与快速预览（3～4 周）

目标：在 DIALux 之前提供趋势判断，降低人工试错次数。

- 解析 IES/LDT 的单位、光通量、功率、对称性、光强采样信息；
- 生成带“预览/近似”标识的工作面网格和热力图；
- 采用已选灯具的配光 SHA-256 作为输入，不允许使用未确认候选；
- 明确预览不包含完整遮挡、反射和可靠 UGR，不能写入最终合规结论。

验收指标：

- 与 DIALux 基准项目平均照度趋势误差目标 ≤ 15%；
- 预览结果页面始终显示求解器版本、输入快照和近似限制；
- 任一配光文件变更会使预览和仿真状态过期。

### 阶段 3：布灯方案搜索（4～6 周）

目标：自动产生可审阅的布灯方案，而不是自动签发设计。

- 先限制为矩形单房间、规则网格、单/双灯具类型；
- 使用约束搜索或 OR-Tools 生成候选位置：边距、灯距、数量、功率密度、遮挡禁区；
- 目标函数至少包含照度均匀性、装机功率、灯具数量和偏离轴网惩罚；
- 输出 A/B/C 方案、不可行原因和每个输入约束；
- 选择方案后生成 DIALux 任务包，由专业软件做最终核验。

验收指标：

- 在基准矩形房间中至少 90% 的案例能产生满足几何约束的候选；
- 不可行时能说明是面积、目标照度、灯具光通量或功率上限导致；
- 不把候选布灯位置称为“照度合格”。

### 阶段 4：接受与模板交付（2～4 周）

目标：形成可发布但受控的正式成果。

- 增加 `DesignAcceptance`，只接受当前 revision 的 `matched` 仿真；
- 注册 PPTX/DOCX/PDF 模板，保存模板 SHA-256、版本和字段 schema；
- `DeliveryPayload` 由确定性代码从冻结快照生成；
- 渲染后检查未替换占位符、表格溢出、文件哈希和日志；
- 未接受版本只能生成带“草稿”标识的文件。

验收指标：

- 任一正式文件可反查项目 revision、仿真 run、灯具和配光文件；
- 模板必填字段缺失时阻止发布；
- 10 份样例渲染通过人工视觉检查，无截断和错位。

### 阶段 5：BIM、在线资料和企业化（按项目需要）

- IFC 只读房间/空间导入，提供确认后写入任务书；
- 在线 RAG 连接器保存 URL、抓取时间、内容哈希、来源等级和审批状态；
- 供应商主数据、价格、交期和品牌政策独立于规范证据；
- 采用队列、对象存储、权限、审计导出和多租户隔离；
- DIALux/Relux 桌面自动化仅作为可选适配器，默认人工运行以控制许可和桌面稳定性风险。

## 8. 资源与部署建议

### 8.1 最小可行团队

- 1 名 Python/FastAPI 工程师：领域模型、导入器、测试和部署；
- 1 名前端工程师：项目状态、结果回灌、热力图和交付页面；
- 1 名照明设计工程师：标准适用性、DIALux 基准、模板与验收；
- 兼职 BIM/数据工程师：阶段 5 再投入。

### 8.2 运行形态

- 试点阶段继续采用当前 SQLite + 项目资产目录；
- 解析和渲染任务放入后台队列，避免阻塞聊天流；
- 生产阶段再将 SQLite 迁移到 PostgreSQL，将配光、原始结果和模板放入对象存储；
- LLM、RAG 和供应商请求均设置超时、重试、限流、缓存与脱敏日志；
- 所有仿真/渲染任务记录求解器版本和输入快照，支持重放。

## 9. 风险与闸门

| 风险 | 影响 | 控制策略 |
|---|---|---|
| LLM 虚构标准或型号 | 工程错误、责任不清 | 证据 ID 强制关联；工具输出优先；无证据就提问或标记未知 |
| DIALux/Relux 桌面自动化不稳定 | 试点不可复现 | 第一阶段只做任务包和结果导入；桌面自动化作为可选适配器 |
| UGR 依赖观察方向和空间几何 | 误报合规 | 只有专业仿真结果可做 UGR 结论，目录 UGR 只作候选字段 |
| 图纸单位/墙线错误 | 面积和布灯错误 | DXF/DWG 解析结果先作为候选；单位、边界、面积必须确认 |
| 供应商字段缺失或变更 | 候选排序失真 | 缺字段标记 `incomplete`；记录抓取时间、解析版本和警告 |
| 在线资料版权/版本 | 规范依据失效 | 离线审批资料优先；在线内容先候选、后审批 |
| 模板误填或漏填 | 正式交付错误 | 冻结快照、字段 schema、渲染检查和用户接受前置 |
| 过早做自动布灯 | 周期长、难验收 | 先完成结果回灌和快速预览，再限定场景做优化 |

Go/No-Go 闸门：

1. 阶段 1 未达到错配拦截 100% 时，不进入自动规则回灌；
2. 阶段 2 未建立 DIALux 基准误差集时，不对外宣传“快速仿真”；
3. 阶段 3 未能输出约束和不可行原因时，不进入方案推荐；
4. 阶段 4 未有用户接受记录时，不生成无“草稿”标识的正式交付物。

## 10. 建议的首个试点

选择一个 20～100 m² 的会议室或视频会议室，固定一套已确认灯具和配光文件，完成以下闭环：

```text
上传 DXF + 任务书
  -> RAG 补齐 GB 50034-2024 参数
  -> 流明法初算和规则校核
  -> DIALux Finder 候选与最终型号确认
  -> 生成 DIALux 交接包
  -> 在 DIALux evo 中人工布灯并仿真
  -> 导入结构化结果并校验 handoff 快照
  -> 不达标则生成下一次修改任务
  -> 达标后人工接受并导出报告草稿
```

试点只追求三个可量化结果：

- 从资料接入到 DIALux 交接包的人工操作时间减少 30%；
- 项目事实、证据、灯具、配光和结果 100% 可追溯；
- 错配或过期仿真 100% 被阻止进入合规结论。

## 11. 最终建议

项目可行，建议立项；但应把产品承诺限定为“可审计的人机协作设计工作台”。近期投入顺序应为：

1. 先完成 DIALux/Relux 结果导入、输入快照核验和修订循环；
2. 再做 IES/LDT 解析和带限制说明的快速预览；
3. 然后在矩形单房间范围内做受约束的布灯方案搜索；
4. 最后做接受记录和模板交付；BIM、在线 RAG、桌面自动化作为企业项目扩展。

不建议当前阶段投入“全自动 CAD 到合规报告”或训练专用大模型。现有代码的版本化、证据链和 DIALux 交接基础已经足够支撑试点，下一步的关键不是扩大聊天能力，而是把仿真结果和用户接受两个质量闸门产品化。
