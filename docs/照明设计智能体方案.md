# 室内照明设计智能体技术方案

> 文档状态：当前实现同步 + 目标交付流程扩展方案  
> 更新日期：2026 年 8 月 5 日  
> 项目定位：可审计的室内照明设计工作台，不以大模型文本替代确定性计算或 DIALux evo 人工复核。
>
> 文中以 **[已实现]** 标记当前可用能力，以 **[规划]** 标记为实现目标但尚未进入代码的能力。

## 1. 目标与边界

系统使用 `langchain.agents.create_agent` 作为流程编排层，结合 SQLite、RAG、确定性照明计算和 DIALux Luminaire Finder，形成可追溯的照明设计工作流。

```text
用户设计任务（文字说明、项目文件）
  → 资料入库、哈希与项目事实提取
  → 离线优先 / 在线可选的 RAG 检索
  → 模型编排工具，形成可追溯任务书
  → RAG 自动补齐照明参数；仅对无法确定项询问用户
  → 初算、规则校核、DIALux 灯具候选与最终型号确认
  → DIALux evo 交接包
  → 用户在 DIALux evo 完成照度、均匀度、UGR 等分析
  → 导入并校验 DIALux 结果，模型给出修订建议
  → 用户确认满意的项目版本
  → 按已注册 PPT/PDF 模板生成交付物
```

系统已经实现“项目、证据、初算、候选灯具、Markdown 报告草稿与 DIALux evo 交接包”的闭环；以下功能仍属于后续阶段：

- IES/LDT 的照度快速预览与热力图；
- 可复现的后端精算求解器；
- 自动布灯、多方案优化与 DIALux 工程文件自动生成；
- 在线 RAG 连接器及其来源审批；
- DIALux evo 结果导入、输入版本核验和结果回灌；
- 用户满意度/设计接受门槛；
- 用户模板驱动的 PPTX、PDF 正式交付。

因此，当前系统不得将浏览器场景、灯具目录字段或流明法初算表述为“照度合格”“UGR 合格”或“DIALux 最终结果”。

### 1.1 推荐端到端交付流程

用户给出的流程是正确方向；建议将“模型分析”细化为可审计的工具编排循环，并把 DIALux 与模板化交付设为明确的质量闸门。

| 阶段 | 输入 | 系统动作 | 用户动作 | 产出 / 闸门 |
|---|---|---|---|---|
| 1. 项目接入 | 文字任务、PDF/DOCX/MD/TXT | **[已实现]** 创建项目，保存资料哈希，文本入库 | 上传资料；补充项目名称 | 可追溯项目与原始资料 |
| 2. 证据检索 | 项目事实、空间用途 | **[已实现]** 离线 RAG 检索；**[规划]** 在线 RAG 补充受控来源 | 仅在资料缺失时指定来源或范围 | 可引用 `Evidence` 集合 |
| 3. 任务书与补参 | Evidence、项目资料 | **[已实现]** 模型调用工具提取事实，RAG 填写照度/Ra/UGR/LPD 等 | 仅确认冲突、缺失或业务偏好 | 版本化 `DesignBrief` |
| 4. 设计初算 | 任务书、空间/灯具条件 | **[已实现]** 流明法初算、规则校核 | 确认必要设计意图 | 可审查初步方案与限制 |
| 5. 灯具选择 | 已确认照明条件（照度/色温/Ra/UGR） | **[已实现]** DIALux 产品检索、详情校验、配光资产归档 | 明确确认最终型号（可多款组合） | 仅含最终型号（可多款）的 DIALux 交接包 |
| 6. DIALux 仿真 | 交接包、真实项目模型 | **人工执行** DIALux evo 计算 | 导入、布灯/修订、运行仿真、导出结果 | DIALux 原始导出文件 |
| 7. 结果回灌 | DIALux 导出、项目/场景/灯具快照 | **[规划]** 解析指标、校验输入一致性、重跑规则校核 | 必要时确认结果归属 | 可验证 `SimulationRun` |
| 8. 修订循环 | 不通过或不满意的结果 | **[规划]** 模型依据差距提出修改，生成新的交接包 | 在 DIALux 中复算 | 满足目标或记录例外 |
| 9. 接受与交付 | 已验证仿真、最终项目 revision、模板 | **[规划]** 锁定交付快照，填充模板并渲染 PPTX/PDF | 明确“满意并发布” | 正式 PPTX、PDF、报告数据包 |

“模型分析”不等于暴露模型内部推理。界面只显示步骤、工具、输入/输出摘要、证据、版本和失败原因；不显示 chain-of-thought。
阶段1、2、3和4已支持常用室内照明模板，工程师可在创建项目时选用普通办公室、会议室或视频会议室模板。模板会预填设计任务书的规范初始值并保存模板与标准引用；它们始终是可编辑的项目输入，不会自动生成规则校核结论或替代项目资料、RAG 证据与人工确认。

当前模板初始值（依据项目资料库中的《建筑照明设计标准》2024）如下：

| 模板 | 维持照度 / lx | UGR | U₀ | Ra | 工作面 / m | 色温 / K | LPD 目标 / W·m⁻² |
|---|---:|---:|---:|---:|---:|---:|---:|
| 普通办公室 | 300 | ≤19 | ≥0.60 | ≥80 | 0.75 | 4000（建议初值） | ≤6.5 |
| 会议室 | 300 | ≤19 | ≥0.60 | ≥80 | 0.75 | 4000（建议初值） | ≤6.5 |
| 视频会议室 | 750 | ≤19 | ≥0.60 | ≥80 | 0.75 | 4000（建议初值） | ≤6.5（按会议室对照初始值） |

其中照度、UGR、均匀度、Ra 与工作面高度来自表 5.3.2；普通办公室和会议室的 LPD 目标值来自表 6.3.5。视频会议室的 750 lx 来自表 5.3.2，LPD 未在表 6.3.5 单列，故界面明确标注为会议室对照初始值。4000 K 是在标准 4.5.1/4.5.2 允许范围内的模板建议值，不是不可调整的强制值。

工程师选择模板后仍可在任务书中修正任意字段；修正后的值写入新的项目 revision，并按既有规则使相关初算、灯具确认或仿真结果重新校核。模板来源仅保存 `template_origin` 元数据，不伪造 `evidence_id`，也不把模板值自动宣称为已采纳规范证据。

## 2. 核心原则

1. **LLM 负责理解、检索编排与解释，不负责虚构工程事实。**
2. **所有项目事实保存到版本化 `ProjectState`，不以聊天记录作为权威数据源。**
3. **规范数值必须来自 RAG 返回的原文证据或项目资料。**
4. **照明参数优先从 RAG 自动填充；只有证据缺失、冲突、不适用，或空间基础条件不能确定时才向用户询问。**
5. **所有计算结论通过确定性模块产生，并保存输入、假设、限制与版本。**
7. **DIALux 产品数据是不可信供应商数据，只能作为候选；最终项目选择和配光下载必须显式确认。**
8. **[已实现] 任务书、最终灯具或配光变更后，旧仿真结果标记为 `stale`。**
9. **离线已审批资料优先于在线检索；在线资料必须保存 URL、抓取时间、内容哈希和来源等级。**
10. **DIALux 导出结果只有在输入版本匹配后才能参与规则校核和正式交付。**
11. **PPT/PDF 的内容来自冻结的交付快照和模板字段映射，模型不能直接、不可控地改写模板文件。**

## 4. 项目数据与版本控制

### 4.1 `ProjectState`

每个项目使用随机十六进制 `project_id` 标识。当前状态与每次写入后的不可变快照保存在 SQLite。

```text
ProjectState
├── project_id
├── revision
├── brief: DesignBrief
├── evidence: Evidence[]
├── calculations: CalculationResult[]
├── rule_checks: RuleCheck[]
├── luminaires: LuminaireCandidate[]
├── luminaire_search_runs: LuminaireSearchRun[]
├── selected_luminaire_ids: string[]
├── simulation_runs: SimulationRun[]
├── open_questions: string[]
├── created_at
└── updated_at
```

写入规则：

- 浏览器的替换式更新必须携带 `expected_revision`；
- revision 不匹配时返回冲突，避免旧页面覆盖新修改；
- 灯具候选追加使用受限 rebase，避免并行搜索互相丢失；
- 任务书改变会重新校验候选灯具，并清空已选最终型号；
- 任务书、最终灯具或配光改变会将已有 `SimulationRun` 标记为 `stale`。

### 4.2 `DesignBrief` 与来源

`DesignBrief` 存放空间类型、面积、尺寸、安装高度、目标照度、色温、Ra、UGR、均匀度、LPD、安装方式和防护等级等输入。

照明参数包括：

```text
target_illuminance_lx
target_cct_k
min_cri
target_ugr
target_uniformity_u0
max_lpd_w_m2
```

当这些值由 RAG 证据自动填充时，`lighting_parameter_sources` 为每个字段保存：

```json
{
  "target_illuminance_lx": {
    "source": "rag",
    "evidence_ids": ["..."],
    "applied_at": "2026-08-05T..."
  }
}
```

RAG 自动填充工具不会覆盖已有的人工确认值或项目资料确认值。需要修改已有参数时，应通过任务书编辑或明确的人工确认流程完成。

### 4.3 存储布局

```text
data/
├── lighting_design.sqlite3
├── chroma/
└── projects/
    ├── {project_id}.photometry/
    │   ├── archives/
    │   ├── extracted/
    │   └── manifest.json
    ├── {project_id}.design-report.md
    └── {project_id}.dialux-task.zip
```

配光资产不进入 Chroma；项目说明和规范文本可作为 RAG 文本资料入库。

### 4.4 仿真、接受与模板交付数据

**[已实现，第一阶段]** `SimulationRun` 已扩展为可保存 DIALux 指标明细、输入快照与验证状态，并新增项目级 `workflow_status` 派生状态。当前实现：

```text
SimulationRun
├── run_id
├── kind: preview | 精算 | dialux_handoff
├── status: pending | running | succeeded | failed | stale | unverified | cancelled
├── input_project_revision
├── solver_version
├── artifact_path
├── error
├── handoff_id                      # 绑定生成该任务包的不可变交接身份
├── input_snapshot_sha256           # 输入快照哈希（含最终灯具、配光哈希）
├── selected_luminaire_ids
├── photometry_sha256_by_luminaire
├── source_file / source_sha256 / source_kind   # 原始结果文件与来源（第一阶段结构化指标）
├── metrics: SimulationMetrics
│   ├── maintained_illuminance_lx
│   ├── minimum_illuminance_lx
│   ├── uniformity_u0
│   ├── ugr
│   └── installed_power_density_w_m2
├── verification_status: matched | mismatch | incomplete | unverified | stale
├── verification_messages
├── parser_version
├── stale_reason
├── created_at / completed_at

ProjectState.workflow_status
  draft → brief_confirmed → preliminary_calculated → luminaires_selected
        → simulation_pending → simulation_verified → needs_revision
```

`DesignAcceptance` 与 `DeliverableTemplate` 仍属于后续阶段：

```text
DesignAcceptance
├── acceptance_id
├── project_revision
├── verified_result_id
├── accepted_by
├── accepted_at
└── note

DeliverableTemplate
├── template_id
├── kind: pptx | docx_pdf | fillable_pdf
├── original_path / SHA-256 / version
├── field_schema
├── render_engine
└── approval_status
```

关键规则：

- **[已实现]** 每个 DIALux 交接包生成不可变 `handoff_id` 与 `input_snapshot_sha256`，并写入 `dialux-task.json` 与 `manifest.json`；
- 用户导入结果时必须选择 `handoff_id` 或同时上传对应 `dialux-task.json`；DIALux PDF/CSV 本身无法证明来源时不能自动判为 `matched`；
- DIALux 结果中任一项目 revision、最终型号、输入快照或配光哈希不匹配时，标记 `mismatch`，不能进入合规校核或正式交付；
- 任务书、最终灯具、图纸或灯具候选变化时，旧 `SimulationRun` 自动标记为 `stale`，`workflow_status` 派生出 `needs_revision`；
- 无法从导出文件解析版本信息时，标记 `incomplete` 或 `unverified`，只允许显示为用户上传资料；
- `DesignAcceptance` 只能引用 `matched` 且当前未过期的仿真结果（[规划]）；
- 正式 PPTX/PDF 只能绑定一个 `DesignAcceptance`；未接受版本只能生成带“草稿”标识的预览（[规划]）。

## 5. RAG 与自动补参

### 5.1 文档入库

支持 `.pdf`、`.docx`、`.md`、`.txt`：

```text
上传文件
  → 格式解析
  → PDF 必要时提交 PaddleOCR 作业
  → 文本分块、嵌入与索引
  → 保存文件哈希、页数、来源类别和索引数量
```

来源类型：

- `standard`：规范、标准、技术手册；
- `project_document`：项目任务书、建筑资料、甲方资料；
- `user_note`：用户补充说明。

`Evidence` 保存原文摘录、定位信息、来源类型、检索时间和相似度分数。模型只能基于实际返回的摘录陈述规范结论。

### 5.2 自动填参工作流

```text
读取 ProjectState
  → 检查缺失照明参数
  → search_evidence(空间用途 + 缺失参数)
  → 判断证据是否明确、适用且无冲突
  ├── 是：apply_rag_lighting_parameters
  │       ├── 写入 DesignBrief
  │       ├── 保存字段级 evidence_ids
  │       └── 将证据附加到项目 revision
  └── 否：ask_user 请求最少必要确认项
```

向用户询问的情形仅包括：

- 检索不到可适用的明确条文或项目资料；
- 多份证据给出互相冲突的数值；
- 空间用途、安装方式、面积、净高或几何条件无法判断；
- 用户明确要求以自身要求覆盖默认规范目标。

系统不得从常识、模型记忆、供应商产品标签或不适用空间条文猜测照度、Ra、UGR、LPD 等数值。

### 5.3 在线 / 离线 RAG 策略

当前系统已实现离线资料库检索；在线 RAG 是后续扩展，不能绕过既有证据审计链路。

```text
检索请求
  → 离线优先：已审批规范、项目资料、历史确认资料
  → 命中不足时，按项目策略启用在线连接器
  → 下载并保存内容快照、URL、抓取时间、SHA-256、来源等级
  → 作为候选资料进入 Evidence
  → 由用户/管理员审批后，才可作为强制性规范依据
```

来源优先级：

1. 项目合同、任务书、甲方确认文件；
2. 已审批且版本明确的规范全文或企业标准；
3. 官方发布机构、政府部门或灯具厂商的原始资料；
4. 行业文章、搜索摘要、论坛和二次转载。

第 4 类只能辅助检索或解释，不能单独填充强制性规范参数。在线连接器应允许项目级禁用，并遵守目标网站许可、robots、访问频率和本地数据留存政策。

每条在线资料至少应保存：

```text
source_url
retrieved_at
content_sha256
source_authority: official | manufacturer | secondary
document_version / publication_date（若可获得）
approval_status: candidate | approved | rejected
```

## 6. Agent 与工具边界

### 6.1 Agent 工作流

`create_agent` 负责选择工具和生成解释，实际工作按下列可观察步骤推进：

```text
读取项目与新增资料
  → 解析项目文件
  → 离线优先、在线可选的 RAG 检索
  → RAG 自动填充照明参数
  → 仅对不确定项 ask_user
  → 初算与规则校核
  → 筛选并确认最终 DIALux 灯具
  → 生成 DIALux evo 交接包
  → 等待用户导入经验证的 DIALux 结果 [规划]
  → 修订循环或用户接受
  → 按模板生成 PPTX / PDF [规划]
```

Agent 必须：

- 每轮涉及项目事实时先读取项目；
- 使用最新 revision 写入；
- 对计算、规则校核、灯具检索、场景构建调用工具；
- 明确区分候选、初算、仿真输入和最终人工复核结论；
- 在用户确认最终型号前不得创建最终灯具选择；
- 在未收到可验证的 DIALux 导出前，不得把初算或产品目录结果写入“仿真结果”；
- 在用户明确接受一个设计 revision 前，不得生成无“草稿”标识的最终 PPT/PDF。

## 7. 确定性初算与规则校核

### 7.1 流明法初算

当前初算模块使用：

```text
所需光通量 = 目标照度 × 面积
灯具数量 = ceil(所需光通量 / (单灯光通量 × 利用系数 × 维护系数))
```

结果保存以下内容：

- 输入面积、目标照度、单灯光通量、单灯功率、利用系数、维护系数；
- 所需光通量、灯具数量、装机功率、装机功率密度；
- 假设和适用限制。

流明法仅用于方案初算，不能替代空间遮挡、反射、灯具配光、观察方向和布灯方式下的精确照度或 UGR 计算。

### 7.2 规则校核

规则校核器只接受显式的 `RuleRequirement`：

```text
metric: illuminance_lx | cri | lpd_w_m2 | ugr | uniformity_u0
operator: min | max
threshold: 数值
evidence_id: 可选的规范证据 ID
```

输出状态为：

- `pass`
- `fail`
- `not_applicable`
- `insufficient_data`

没有 evidence 或观测输入时，系统不会伪造合规结论。

## 8. DIALux Luminaire Finder 集成

### 8.1 调用流程

```text
prepare_luminaire_search
  → 校验空间用途和至少一项关键照明条件（照度/色温/Ra/UGR）
  → search_luminaires
      ├── DIALux 列表 JSON
      ├── 并发读取候选详情 HTML
      ├── 标准化功率、光通量、色温、Ra、UGR、IP
      ├── 与搜索条件和当前任务书分别校验
      └── 保存 LuminaireSearchRun 与候选
  → get_luminaire_detail（按需）
  → 用户确认
  → select_luminaires
```

列表接口使用：

```text
/{language}/{skip}/{count}/search/query/a231?ft={keyword}&bf={brand_id}
```

详情页使用：

```text
/{language}/article/{luminaire_id}
```

### 8.2 防御性策略

外部目录是未版本化的 JSON/HTML 数据源，客户端具有以下保护：

- 超时、重试、请求节流、TTL 缓存和熔断；
- 总搜索截止时间与受限并发详情读取；
- 中文关键词无法稳定命中时的英文关键词回退；
- 品牌别名、色温容差、UGR 解析与 IP 比较；
- 详情解析失败、字段缺失和响应结构变化的结构化错误；
- 保存 `LuminaireSearchRun` 记录请求、候选 ID、解析版本、耗时和警告；
- 供应商详情只以摘要形式传入模型，不将原始 HTML 或自由文本当作指令。

搜索条件以目标照度、色温、显色指数（Ra）和 UGR 为主，从已确认任务书自动采用；功率、IP、品牌等其他条件仅在用户明确说明时加入。UGR 是优选条件（供应商常不提供 UGR 数据），解析到供应商声明值时参与排序，最终眩光值仍须在 DIALux evo 中核验。

候选可能符合本次搜索条件，却不符合当前项目任务书。例如搜索允许 `3500K ±500K`，而项目任务书要求精确 `3500K`。此类候选仍会保存以便追溯，但其 `project_brief_matching_status` 会标记为不符合，无法被设为最终选定项。

### 8.3 最终选择与配光资产

只有 `selected_luminaire_ids` 中的最终型号可以下载配光资产和进入交付包。最终选定不限于单款：房间通常由多款灯具组合（如基础照明、重点照明、应急照明），所有选定型号一次性写入 `select_luminaires`，并一起进入配光下载与任务包。

```text
最终选择
  → DIALux 详情页发现同源 photometry ZIP
  → 下载 ZIP
  → 解压 IES / LDT / ULD
  → 保存原 ZIP、文件 SHA-256 和资产清单
  → 生成 DIALux 任务包
```

配光 ZIP 处理限制包括成员数量、压缩率、单文件和总解压大小、加密文件、路径安全和流式解压限制，以防止 ZIP Slip 与压缩炸弹。

当前阶段的 IES/LDT/ULD 文件用于可追溯交接，不代表系统已经完成照度求解。

## 9. 图纸分析

**[已实现]** 支持导入 `.dxf`（以及本机安装 ODA File Converter 时的 `.dwg`），解析单位、图层、文字标注、闭合房间边界候选与面积候选。DIALux 专属图层（`DLX_*`）按米解释；分段墙线网络经 shapely `polygonize` 重构闭合轮廓。解析结果是**候选事实**：只有经用户确认或规则自动选定、并写入任务书（面积、长宽、空间名称）的几何才参与计算与选型。历史快照中旧的 `plan`/`scene` 字段在读取时丢弃。

以下能力不属于当前图纸模块，也不得表述为已实现：三维场景构建、墙体/门窗自动识别结论、布灯位置自动方案、以及基于图纸的照度/均匀度/UGR 仿真。这些仍需在 DIALux evo 或等效软件中完成。

## 12. DIALux 交接、结果回灌与模板交付

### 12.1 [已实现] Markdown 报告草稿

设计报告包含：

- 项目任务书与已确认输入；
- 采用的规范证据及来源定位；
- 流明法输入、结果、假设和局限；
- 规则校核结果；
- 候选灯具与最终选定状态；
- 待确认事项；
- DIALux evo 或等效仿真的人工复核声明。

### 12.2 [已实现] DIALux 任务包

任务包仅包含最终选定灯具及其可用配光资产，并记录：

- 项目 revision；
- 最终型号与 DIALux ID；
- 配光 ZIP、解压文件和 SHA-256；
- 当前任务书、候选/选择状态；
- 图纸解析状态、比例校准信息、场景摘要和待补充项；
- 必须在 DIALux evo 完成的复核项。

最终选定灯具确认后，当前版本生成包含 ULD/IES/LDT 配光资产的 DIALux 任务包，由用户在 DIALux evo 中人工导入并核对。最终选定可为多款灯具的组合，全部选定型号一起进入任务包。桌面自动提交属于后续可选适配器，尚未暴露给当前 Agent，也不能把任务包生成描述为已完成导入或仿真。

没有最终选定灯具或没有明确计算边界时，任务包不能被描述为仿真结论。

### 12.3 [规划] DIALux 结果回灌与修订循环

用户在 DIALux evo 中完成模型调整和仿真后，应上传导出的结果文件，而不是仅在聊天中口述“照度合格”。推荐的导入优先级为：

1. DIALux 导出的结构化 CSV 或可稳定解析的结果表；
2. DIALux 导出的 PDF 计算报告；
3. 系统受控的指标表单，作为无法导出时的兜底方式。

导入时应要求或解析以下字段：

```text
项目 / 房间名称
工作面高度与计算面
维持平均照度 Eavg
最小照度 Emin
均匀度 U0
UGR（适用时）
装机功率与 LPD
灯具型号、数量、位置或灯具清单
DIALux / 求解器版本
导出时间
```

回灌流程：

```text
用户上传 DIALux 结果（结构化指标 + handoff_id）
  → 选择对应 handoff_id，或同时上传该交接包中的 dialux-task.json
  → 保存原始文件和 SHA-256（第一阶段：结构化指标先行，PDF/CSV 解析为后续阶段）
  → 解析为结构化指标
  → 与 handoff snapshot、项目 revision、最终型号、配光哈希比对
  ├── matched：写入可验证 SimulationRun（状态 succeeded，verification_status=matched）
  │     → 使用已保存规范证据做确定性规则校核
  │     → 模型解释差距、风险和可选修订
  ├── mismatch：提示用户重新导出或选择正确的项目快照
  └── incomplete：仅显示已解析部分，不得生成“通过”结论
```

> **[已实现，2026-08]** 第一阶段已完成最小闭环：
>
> - `SimulationRun` 扩展为可保存结构化指标（`SimulationMetrics`）、输入快照哈希、handoff_id、最终灯具与配光哈希、来源与验证状态；
> - DIALux 任务包现在生成不可变 `handoff_id` 与 `input_snapshot_sha256`，并写入 `dialux-task.json` / `manifest.json`；
> - 新增 `POST /api/projects/{project_id}/dialux-results` 及其列表/详情端点，导入结构化结果并与当前任务包校验，返回 `matched` / `mismatch`；
> - 任务书、最终灯具、图纸或灯具候选变化时，旧 `SimulationRun` 自动标记为 `stale`，并派生项目 `workflow_status`（`simulation_pending` / `simulation_verified` / `needs_revision` 等）；
> - CLI 新增 `import-dialux-result` 子命令。
>
> 尚未实现：DIALux PDF/CSV 自动解析、规则校核自动重跑、设计接受与模板化正式交付（见 12.4 及后续阶段）。

若 DIALux 导出只包含照度数值、无法提供灯具清单或手工修改过模型，系统只能把它标记为 `unverified`。用户可以将它作为参考资料，但不能用于自动规则校核、用户接受或正式模板交付。

若结果未达标，系统应输出“下一次 DIALux 修改任务”，例如增减灯具、替换已确认候选、修改安装方式或要求补充反射率；随后生成新的 DIALux 交接包。这个循环由用户在 DIALux evo 中执行，直到指标达标或用户接受有记录的例外。

### 12.4 [规划] 用户模板驱动的 PPTX / PDF 交付

模板必须先注册、解析并版本化，再允许生成正式交付物。系统不应让模型直接修改二进制文件或根据自然语言猜测版式。

推荐模板格式：

| 交付物 | 推荐模板 | 处理策略 |
|---|---|---|
| 演示稿 | `.pptx` | 固定版式 + 文本占位符 + 命名图片/表格槽位，输出新的 `.pptx` |
| 报告 PDF | `.docx` 模板后转 PDF | DOCX 占位符填充后由受控渲染器导出 PDF |
| 既有 PDF 表单 | 含 AcroForm 字段的 `.pdf` | 按字段名写入，不改变原模板布局 |
| 静态 PDF | 仅在提供字段坐标映射时支持 | 作为最后选择，必须人工视觉复核 |

用户提供模板时，应同时提供或确认：

```text
模板名称与版本
允许的输出格式：PPTX / PDF
每个占位符或命名槽位的字段含义
是否允许使用灯具图片、DIALux 结果截图
封面、页眉页脚、签字页和保密标识规则
缺失字段的显示方式：留空 / N.A. / 阻止交付
```

建议统一占位符契约：

```text
{{project_name}}
{{project_id}}
{{project_revision}}
{{design_brief_summary}}
{{evidence_table}}
{{preliminary_calculation_table}}
{{selected_luminaire_table}}
{{dialux_result_summary}}
{{rule_check_table}}
{{open_questions}}
{{acceptance_note}}
```

表格、灯具清单、证据列表和多房间指标不能简单替换为长文本。模板注册阶段应声明其渲染方式，例如固定行数表格、可复制的表格行、命名图片占位符或预定义的附录页。

正式渲染流程：

```text
用户确认满意
  → accept_design 冻结 project revision + verified SimulationRun
  → 选择已审批模板
  → 从冻结快照构建 DeliveryPayload
  → 校验模板必填字段、版本和数据完整性
  → 渲染 PPTX / PDF
  → 检查未替换占位符、页数、文件哈希和渲染日志
  → 用户下载正式交付物
```

`DeliveryPayload` 应由确定性代码从项目快照生成，至少包含任务书、证据、初算、规则校核、最终灯具、DIALux 验证结果、接受记录和免责声明。模型只能为“设计说明”“风险提示”等允许的文本字段生成受限草稿，数值、表格和版本号必须来自快照。

## 13. 安全与可靠性要求

| 风险 | 当前控制措施 |
|---|---|
| 聊天记录覆盖项目事实 | 项目状态独立保存，revision 冲突检查 |
| 模型虚构规范 | 规范结论必须来自 `search_evidence` 返回的原文 |
| 缺失参数时盲目提问 | 先 RAG 检索并自动填充，不能确定才 `ask_user` |
| RAG 覆盖人工参数 | `apply_rag_lighting_parameters` 不覆盖人工/项目资料确认值 |
| DIALux 上游不稳定 | 超时、重试、缓存、限流、熔断、结构化错误 |
| 供应商提示注入 | 模型仅接收受限摘要，详情字段标记为不可信 |
| 非项目候选 ID 被读取 | 详情工具只读取已保存项目候选；历史 ID 要求刷新搜索 |
| 配光 ZIP 攻击 | 同源下载、大小限制、成员数限制、压缩率限制、加密检查、路径安全 |
| 旧仿真继续使用 | **[已实现]** 任务书、最终灯具或配光更新时将旧 `SimulationRun` 标记 `stale` |
| 调试泄漏敏感信息 | 调试摘要限长并脱敏 key/token/secret/password 等字段 |
| 在线资料不可靠 | **[规划]** 离线审批资料优先；在线资料保存快照和来源等级，审批后才可作为规范依据 |
| DIALux 结果错配 | **[规划]** 校验项目/场景 revision、最终型号和配光哈希；不匹配即阻止正式结论 |
| 模板内容错填 | **[规划]** 模板版本、字段 schema、交付快照和渲染日志必须绑定；未替换字段阻止交付 |
| 未经用户确认即正式发布 | **[规划]** `DesignAcceptance` 是正式 PPT/PDF 的前置条件 |

## 16. 运行与验证

### 16.1 后端

默认端口可用时：

```powershell
uv run uvicorn lighting_agent.web_api:app --reload --port 8000
```

若本机端口 `8000` 被占用或受权限策略限制，可改用其他端口，例如：

```powershell
uv run uvicorn lighting_agent.web_api:app --reload --port 8001
```

### 16.2 前端

后端使用 `8001` 时：

```powershell
cd web
$env:LIGHTING_API_URL = "http://127.0.0.1:8001"
npm run dev -- --port 3000
```

前端默认通过 `/backend` 转发到 `LIGHTING_API_URL`，未设置时默认使用 `http://127.0.0.1:8000`。

### 16.3 检查命令

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"
uv run pytest -q
uv run python -m compileall -q src tests

cd web
npm run typecheck
npm run build
```
