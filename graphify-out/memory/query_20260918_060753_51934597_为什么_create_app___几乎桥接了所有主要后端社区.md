# Q: 为什么 create_app() 几乎桥接了所有主要后端社区

## Answer

图谱把 `create_app()` 识别为后端的应用装配入口，而不是单一业务算法。它位于 `src/lighting_agent/web_api.py:L874`，度数为 119：其中 45 条是 `calls`、16 条是 `uses`、3 条是 `references`，另有 55 条 `contains` 关系。也就是说，它既初始化基础设施，又在同一个工厂里定义并注册大量 API handler，所以天然会成为跨社区桥。

关键桥接路径包括：

- 运行时与基础设施：`Settings`（L891）、`DialuxAPI`（L890）、`WorkspaceProjectStore`（L883）、`WorkspaceEvidenceStore`（L886）、`ChatSessionStore`（L899）、`PhotometryAssetStore`（L925）、`configure_runtime_services()`（L913）、`build_agent()`（L1000）。
- 项目与版本数据：`ProjectStore`（L876）、`ProjectState`（L930）、`DesignBrief`（L1080）、`RevisionConflictError`（L1144）。其中 `ProjectStore`、`ProjectState`、`DesignBrief` 的部分连接被标为 `INFERRED`，应视为待核实的模型推断，而不是确定调用。
- 业务端点族：文档/项目端点（如 `add_document()` L1431）、聊天生命周期（`chat()` L2429、`stream_chat()` L2479）、照度与规则计算（`evaluate_illuminance()` L1130、`calculate_lumen_method()` L1452、`check_design_rules()` L1982）、DIALux 结果导入（`import_dialux_result()` L1133）、配光解析/预览（L2227、L2300）以及交付物生成（L2396、L2408、L2411）。

因此它连接到项目文档、SQLite 持久化、模型运行时、DIALux、聊天、初算、照度验证、配光资产和交付物等社区。这个“几乎全后端”的现象主要是架构位置造成的：所有跨领域依赖在应用启动时汇合，所有 HTTP 路由又从这个工厂向外展开。测试也通过 `make_client()` 等入口调用它（例如 `tests/test_web_api.py:L151`），所以测试社区也被接入。
